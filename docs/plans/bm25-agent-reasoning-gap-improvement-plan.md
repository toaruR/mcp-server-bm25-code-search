# 「Agent 推論・比較・再検索」ギャップ解消 改善プラン

本ドキュメントは、理想アーキテクチャ

```
大量の文書 → BM25全体検索 → Top-N候補 → Agent(推論・比較・再検索) → LLM
```

と現行実装との差分（[bm25_search/search.py](../../bm25_search/search.py)・[bm25_search/mcp_server.py](../../bm25_search/mcp_server.py) はBM25 Top-K検索を1回実行して返すだけで、「推論・比較・再検索」を行う独立した層が存在しない）を踏まえ、その差分をどう埋めるかの改善プランをまとめたものである。**本ドキュメントは計画のみであり、実装は行わない。**

---

## 1. 現状分析（再掲）

| 理想図の段階 | 現状の実体 |
|---|---|
| BM25全体検索 | [search.py](../../bm25_search/search.py) の `search()`。FTS5 `bm25()`、filepath×3.0重み付けのみ。埋め込み/意味検索なし |
| Top-N候補 | `top_k` 件をスコア降順で返すだけ（[search.py:275-311](../../bm25_search/search.py#L275-L311)）。多様化・重複排除なし |
| Agent（推論・比較・再検索） | **サーバー内に実体なし**。呼び出し元LLM（Claude Code本体など）に丸投げされている |
| LLM | 呼び出し元LLMが兼任。サーバーが渡せる誘導材料は「0件時の固定メッセージ」1つのみ（[search.py:352-355](../../bm25_search/search.py#L352-L355)） |

追加で判明した制約要因：
- チャンク分割は行番号ベースの機械的な80行/20行オーバーラップ固定（[indexer.py:39-43](../../bm25_search/indexer.py#L39-L43)、関数・クラス境界を考慮しない）。
- MCPサーバーは**意図的に完全ステートレス**（SEP-2567/2575準拠、[mcp_server.py:9-14](../../bm25_search/mcp_server.py#L9-L14)）。ロードバランサ配下でも動く設計方針であり、これを崩す変更は要合意。
- 設計要件1（[bm25-multi-agent-search-skill-design.md](bm25-multi-agent-search-skill-design.md) 要件1）で「外部重厚ライブラリ非依存・標準ライブラリ+SQLite3ベース」が明記されており、埋め込み/ベクトル検索/LLMリランクの追加はこの方針と衝突する。

---

## 2. 改善方針の全体像

「Agent 推論・比較・再検索」をサーバー内にLLMとして持ち込む（＝理想図を額面通り実装する）のはコスト・レイテンシ・設計方針（標準ライブラリのみ）の観点で推奨しない。代わりに、

1. **呼び出し元LLM（既存のAgent層）がより良く「推論・比較・再検索」できるよう、サーバーが渡す情報を厚くする**
2. **サーバー側で機械的に済む「比較」（重複排除・多様化）は先に済ませてノイズを減らす**
3. **チャンク精度を上げてTop-N候補そのものの比較可能性を上げる**

の3方向で、ステートレス設計・軽量ライブラリ方針を維持したまま差分を縮める。

### 2.1 ファイル数・文章量が少ない場合の効果差

BM25はIDF（希少語ほど重要視する統計）に依存するため、コーパスが小さいと候補間の統計的な差が出にくく、施策によって規模依存性が大きく異なる。着手順を決める際はこれを考慮する。

| 施策 | 小規模コーパスでの効果 | 理由 |
|---|---|---|
| 1-A 同一ファイル内チャンク多様化 | 効きにくい | チャンク重複は1ファイルが80行を超えて複数チャンクに分割される場合にのみ発生（[indexer.py:39-43](../../bm25_search/indexer.py#L39-L43)）。小さいファイルは1ファイル=1チャンクで重複自体が起きない |
| 2-A 構造境界考慮のチャンク分割 | 効きにくい | 同上。80行未満のファイルばかりなら関数がチャンクをまたぐこと自体が稀 |
| 1-B 比較材料（スコア差・分布）の付与 | 効く | 候補が2〜3件でも「1位が突出/僅差多数」の判断材料は有用。IDFのばらつきが少ない分、スコア差がむしろ解釈しやすい |
| 1-C 低確信時フォールバック拡充 | むしろ効きやすい | 小規模コーパスほど該当語を含む文書が絶対的に少なく、ヒット薄・0件が起きやすいため、再検索誘導の出番が増える |
| 1-D SKILL.mdへの再検索ループ明文化 | 効く | コード側の統計と無関係にAgent層の振る舞いを規定するため規模非依存。小規模なら「探しても無いものは無い」と早めにgrep/globへ切り替える判断がむしろ重要 |
| 2-B 複数クエリのファンアウト | 効く | 索引が小さいほど1クエリでの再現率が不安定になりがちで、言い換えクエリでの再現率底上げが効きやすい |

**結論**: 小規模コーパスでは 1-A・2-A（チャンク多様化・構造境界分割）はほぼ無意味な一方、1-B・1-C・1-D・2-B（比較材料の付与・低確信フォールバック・SKILL.md明文化・複数クエリファンアウト）は規模に関係なく、むしろ小規模の方が効きやすい。対象プロジェクトが小規模な場合は Phase 1 の中でも 1-B/1-C/1-D を優先し、1-A は後回し（または対象外）にする。

### 2.2 数百ファイル規模での効果差

数百ファイル規模は「小規模」と「大規模」の中間にあたり、2.1で無効だった施策が効き始める転換点になる。

| 施策 | 数百ファイル規模での効果 | 理由 |
|---|---|---|
| 2-B 複数クエリのファンアウト | 最も効く | 語彙の多様性が増え、単一クエリでの再現率のブレが顕在化する。言い換えクエリでの底上げ効果が最大化する規模帯 |
| 1-B 比較材料（スコア差・分布）の付与 | 効く | IDF統計がある程度安定し始め、スコア差が「ノイズ」ではなく「意味のある差」として使えるようになる |
| 2-A 構造境界考慮のチャンク分割 | 効き始める | 80行を超えるファイル（モジュール・クラス定義など）が普通に出てくるため、固定長分割が関数を分断するケースが実際に発生し始める |
| 1-A 同一ファイル内チャンク多様化 | 効き始める | 同上の理由で、大きめファイルの隣接オーバーラップチャンクがTop-Kを埋める場面が現実に出てくる |
| 1-C 低確信時フォールバック拡充 | 効果は相対的に低下 | ヒットする文書の絶対数が増えるため0件・薄ヒットの発生頻度自体は下がる（無効ではない） |
| 1-D SKILL.mdへの再検索ループ明文化 | 引き続き効く（規模非依存） | Agent層の振る舞い規定なのでどの規模でも一定の効果 |

**結論**: 数百ファイル規模では 2-B → 1-B → 2-A/1-A の順で投資対効果が高い。1-C/1-D は優先度を据え置き、3-A・3-B は依然としてこの規模帯特有のメリットが薄いためPhase 3のまま据え置く。

## 3. 施策一覧（優先度別）

### Phase 1（低リスク・即着手可能／コード変更小〜中）

| # | 施策 | 概要 | 影響箇所（想定） |
|---|---|---|---|
| 1-A | ✅**実装済み** 同一ファイル内チャンクの多様化 | 20行オーバーラップにより隣接チャンクが上位を独占しやすい。同一 `filepath` の隣接 `start_line` チャンクが連続してTop-Kを埋める場合に間引く簡易フィルタをBM25結果取得後に追加（プールを`top_k`より広めに取ってから多様化）。スコア計算自体（bm25()）は変更しない | `search.py: search()/_diversify_same_file()` |
| 1-B | ✅**実装済み** 結果メタデータに比較材料を追加 | 各結果のスコアに加え、`top1`との相対差（gap）やスコア分布の要約（例: 上位1件が突出/僅差多数、など）を`structuredContent`に付与。呼び出し元LLMの「候補が拮抗しているか」の判断材料にする。サーバーはヒントを渡すだけで判断はしない | `search.py: compute_confidence()/format_json()`, `mcp_server.py: handle_tools_call()` |
| 1-C | ✅**実装済み** 低確信時フォールバックの拡充 | 現状「0件」時のみ固定メッセージ。ヒット件数が閾値未満、または上位スコアが閾値以下の場合にも「同義語・別粒度キーワードでの再検索を推奨」等の構造化ヒントを追加返却 | `search.py: low_confidence_hint()/format_json()` |
| 1-D | ✅**実装済み** SKILL.md に再検索ループの型を明文化 | 現状は「0件ならgrep/globへ」の一文のみ。「初回検索→結果吟味→薄い場合は言い換えて最大N回再検索→それでもダメならgrep/glob」という具体的手順を明記し、呼び出し元LLM（＝Agent層）の振る舞いを標準化する。**コード変更ゼロ** | `skills/bm25-search/SKILL.md` |

### Phase 2（中コスト・Top-N候補の質そのものを上げる）

| # | 施策 | 概要 | 影響箇所（想定） |
|---|---|---|---|
| 2-A | ✅**実装済み** 構造境界を考慮したチャンク分割 | 現行の行数固定80/20分割は関数・クラスを分断しやすく、Top-N候補間の比較を難しくしている。対応言語（.py/.ts/.go等）から段階的に、関数/クラス境界にオーバーラップをスナップする方式を導入。非対応言語・フォールバックは現行の固定長方式を維持。**実装は言語別パーサではなく、空行検出による言語非依存の前方スナップヒューリスティックを採用**（対応言語判定は行わず、全対象拡張子に一律適用） | `indexer.py: chunk_lines()/_snap_end_to_blank_line()` |
| 2-B | ✅**実装済み** 複数クエリのサーバー内ファンアウト | `search` ツールに `queries: string[]`（複数の言い換えクエリ、最大5件）を受け付けるオプションを追加し、サーバー内で一括発行→RRF (Reciprocal Rank Fusion, k=60) でスコア統合して1回の応答にまとめる。呼び出し元の再検索ラウンドトリップ回数を削減。**1リクエスト内で完結するためステートレス性は維持** | `search.py: search_multi()`, `mcp_server.py: handle_tools_call()` |

### Phase 3（要合意／トレードオフが大きい）

| # | 施策 | 概要 | 懸念点 |
|---|---|---|---|
| 3-A | 軽量な追加ヒューリスティックスコア | 埋め込みは導入せず、シンボル完全一致ボーナス・隣接語ボーナスなど軽量な追加項をBM25スコアに加点する案 | 標準ライブラリ方針は維持できるが、スコアリングの説明可能性が下がる。要ベンチマーク |
| 3-B | オプトインの検索セッションRPC | 明示的に別RPC（例: `search/session`）としてのみ状態を持たせ、コアの`search`はステートレスのまま維持する案 | ステートレス設計（SEP-2567/2575）という明確な設計意図に触れるため、採用するか自体を要合意 |

### 見送り推奨

- **サーバー内にLLM/サブエージェントを組み込んで比較・再検索させる案**（理想図の「Agent」ボックスをそのまま実装する案）：レイテンシ・コスト増、標準ライブラリ方針（設計要件1）との衝突、「ツールは薄く保ち、推論は呼び出し元LLMに任せる」という現設計思想との不整合により見送り。理想図の「Agent」層は引き続き呼び出し元LLM（SKILL.mdで振る舞いを規定）に担わせるのが妥当と判断する。
- **埋め込み/ベクトル検索の全面導入**：同様に設計要件1（外部重厚ライブラリ非依存）と衝突するため見送り。必要になった場合はオプトインの別ツール（例: `search_semantic`）として切り出す方向で再検討。
